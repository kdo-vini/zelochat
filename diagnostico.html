🟡 Importante — risco crescente
AppShell monolítico
Dívida estrutural
ZeloChat
O componente central do frontend concentra estado global, navegação, Kanban, notificações, pedidos e integrações. Já recebeu lazy-loading e otimizações de re-render, mas a estrutura não foi separada em hooks e módulos independentes.
Impacto
Cada nova feature exige tocar no mesmo arquivo de 1300+ linhas. Risco de regressão cresce a cada sprint. Onboarding de novo desenvolvedor é lento.
Quando resolve
Próxima feature que exija novo estado global. Idealmente antes de qualquer expansão multi-tenant no frontend.
Ecossistema
Só ZeloChat. ZeloMenu tem páginas separadas (store, cart) que não passam pelo AppShell.
Pipeline crítico sem teste automatizado
Risco de regressão
ZeloChat ZeloMenu
O caminho webhook → IA → pending order → confirmação → Kanban → notificação ao cliente não tem nenhum teste integrado. Só existem testes de funções isoladas (regras de agenda, lógica de confirmação, guardrails).
Impacto
Qualquer alteração em server/ai.ts, server/router.ts ou server/messageHandler.ts é "torcer pra não quebrar". O bug de pedido duplicado (que já aconteceu em prod) só foi pego porque o cliente reclamou.
Quando resolve
Antes da próxima mudança no pipeline de pedido. O risco atual é baixo porque ninguém está mexendo nesse caminho, mas qualquer sprint que toque em server/ai.ts deve incluí-lo.
Afeta ZeloMenu
Sim — pedidos do ZeloMenu passam pelo mesmo pipeline de confirmação e Kanban.
Bucket de fotos/áudios público por limitação do Whatsmiau
Trade-off aceito
ZeloChat Whatsmiau
O bucket zelochat-media continua público porque o Whatsmiau precisa de URLs públicas para baixar e enviar mídia no WhatsApp. A mitigação aplicada (paths não-enumeráveis com slug de 128 bits + limpeza de arquivos históricos) elimina o risco de varredura, mas não o risco de um link vazar individualmente.
Impacto
Baixo hoje. Um link só vaza se alguém explicitamente compartilhar. Mas é um passivo LGPD: fotos de cliente estão num bucket público, mesmo que não enumerável.
Quando resolve
Quando o Whatsmiau suportar download autenticado, ou se criarmos um proxy próprio que baixa e reenvia sem expor a URL original.
Ecossistema
Só ZeloChat. ZeloMenu usa o mesmo bucket? Não — ZeloMenu tem publicação própria em storage separado.
🔵 Tático — deve ser feito, não quebra agora
Bug: consulta de pedido em entrega usa status inexistente
Bug conhecido
ZeloChat
Em server/ai.ts:1778, a query que busca pedidos em rota usa 'dispatched' (inexistente no banco) em vez de 'out_for_delivery'. Pedidos que já saíram para entrega nunca entram no contexto da IA.
Impacto
A IA não sabe que o pedido do cliente já saiu para entrega. Se o cliente perguntar "e meu pedido?", a IA pode responder algo genérico em vez de "saiu para entrega às 19:30".
Correção
Uma linha: trocar 'dispatched' por 'out_for_delivery'. Mas ai.ts é função crítica (ver CLAUDE.md) — requer verificação manual antes.
Drift de documentação vs código no webhook
Inconsistência
ZeloChat
O teste tests/auditFixGuardrails.test.ts e a documentação esperam a env WEBHOOK_ALLOW_MISSING_TOKEN_DURING_ROLLOUT, mas o código atual usa WEBHOOK_REQUIRE_TOKEN como opt-in estrito e aceita token ausente por padrão.
Impacto
Só o teste automatizado quebra. Produção funciona normalmente, mas o teste falso-positivo reduz confiança na suíte.
Correção
Alinhar teste + documentação com o comportamento real do código, ou alterar o código para corresponder ao que o teste espera.
Bundle do frontend acima de 500 KB
Performance
ZeloChat
O chunk principal (index-WPPUGIRI.js) tem 597 KB (168 KB gzip). O Vite alerta quando passa de 500 KB. Isso não inclui o ZeloMenu (que é um build separado).
Impacto
Primeiro carregamento ~0.5s mais lento em 3G. Navegação subsequente é rápida (cache).
Correção
Separar bibliotecas grandes em chunks vendors. Ou adiar quando o AppShell for refatorado (aproveita para dividir em módulos).
Dependências principais desatualizadas (major)
Manutenção
ZeloChat ZeloMenu
Várias dependências estão uma ou mais majors atrás: express@5, vite@8, stripe@22, typescript@6. Cada uma exige migração dedicada (especialmente Express 4→5 e Stripe).
Impacto
Nenhum hoje. Mas quanto mais tempo passa, maior o salto e mais coisa quebra na migração. Stripe especialmente — versões muito antigas perdem suporte a novas APIs.
Ordem recomendada
TypeScript 6 (só tipo, menor risco) → Stripe 22 (testar billing) → Vite 8 (testar build) → Express 5 (testar rotas). Cada um em PR separado.
Afeta ZeloMenu
Sim, compartilham as mesmas dependências do backend (Express, Stripe). O frontend do ZeloMenu é build separado.

⚪ P1 adiados — só relevantes se sair do single-node

Três achados do audit foram classificados como "resolve quando sair do single-node backend". Hoje o ZeloChat roda em um servidor só. Se escalar para múltiplas réplicas, esses viram P0.

P1.16 — recordAiFailure em memória
Adiado
O contador de falhas consecutivas da IA está na memória do processo. Com duas réplicas, cada uma tem metade das falhas → nenhuma dispara a escalação automática.
Resolve quando
Backend for multi-replica. Até lá, single-node significa contador único.
P1.17 — configStore desync entre réplicas
Adiado
O cache de configurações (cardápio, horários) é local. Duas réplicas podem ter versões diferentes do cardápio ao mesmo tempo → IA responde com preços desatualizados em uma delas.
Resolve quando
Multi-replica. Precisa de Redis ou cache centralizado.
P1.43 — getAllSessions table scan
Adiado
A listagem de conversas carrega tudo do banco e agrupa em memória. Com 2 mil+ sessões por loja, começa a ficar lento.
Resolve quando
Cliente atingir ~2.000 conversas. Hoje nenhum passou de 500.
🔗 Pontes entre ecossistemas (ZeloChat × ZeloMenu × ZeloPDV)

Riscos que não são de código, mas de coordenação entre os dois produtos.

Tabelas compartilhadas com ZeloPDV
Regra de ouro
ZeloChat ZeloPDV
ZeloChat e ZeloPDV compartilham o mesmo banco Supabase. ZeloChat NUNCA pode ALTERAR tabelas do PDV (empresa_perfil, subscriptions, produtos, categorias, subcategorias, etc.). Só adiciona colunas próprias em empresa_perfil. Isso já causou alertas no passado.
Impacto
DDL errado deste repo quebra o PDV silenciosamente — faturamento, caixa, catálogo. Já documentado em CLAUDE.md, mas não há barreira técnica, só processo manual.
Mitigação
Nenhuma nova, além da documentação existente. Ideal: um CI job que detecta ALTER TABLE em tabelas PDV-owned e bloqueia o PR.
ZLM-203 — slug público bloqueado no ZeloPDV
Dependência externa
ZeloChat ZeloMenu ZeloPDV
A coluna zelomenu_slug em empresa_perfil precisa ser criada pelo repo do ZeloPDV (a tabela é PDV-owned). O código do ZeloChat já está pronto para ler e servir o slug — falta a DDL do outro lado.
Impacto
ZeloMenu funciona sem slug (fallback para humano). Cliente sem slug não recebe link do cardápio. Bloqueia rollout automático de novas lojas.
O que fazer
Abrir issue no repo ZeloPDV para criar a coluna. Depois migration daqui para popular os slugs existentes.
ZLM-205 — rollout de entitlements (parcialmente bloqueado)
Dependência externa
ZeloChat ZeloMenu ZeloPDV Stripe
A parte local (resolver de capability) já está entregue. Falta: price IDs Stripe para o addon ZeloMenu + flag has_zelo_menu no PDV + grandfathering da Casa dos Salgados e migração da Agreste.
Impacto
Não bloqueia clientes existentes. Impede vender ZeloMenu como addon para novos clientes até os prices estarem no Stripe e a flag no banco.
O que fazer
Criar prices no Stripe Dashboard + abrir issue no ZeloPDV para a coluna. Migração da Agreste precisa de comunicação com o cliente.
